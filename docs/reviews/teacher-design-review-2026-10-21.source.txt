从用户角度，这个结构说明五件事：
玩家的真相只有一个文件：dist/index.html。src 里 49 个文件改到什么程度，玩家看到的都是旧的，直到有人跑一次 build-game.cjs。C 改了源码没构建，玩家端毫无变化——而测试跑的恰恰是 dist，所以测试全绿也可能玩家什么都没收到。
学习成果没有家：全部存在当前浏览器里。以"学习学会为目的"衡量，这是最硬的一条——学会的证据不能迁移、不能分享、清一次缓存就没，唯一出口是成长手记里一个不起眼的导出按钮。学会的东西留在设备上，不在人身上。
说明书给了一条大多数玩家走不通的路：导入知识库需要本机服务加 API 密钥，而直接双击 dist/index.html 是最可能的打开方式。引导却把"换成自己的材料"放在显眼位置——显眼度和可达性不匹配。
29 张美术和 4 个 HTML 入口是用户资产：对玩法零贡献，对老玩家的识别度是全部。重构前该问的不是"能不能合并"，而是"老玩家还找得到原来的东西吗"。
229 个玩家不可见的文件，是"敢改"的前提：这个仓库约 30% 是给玩家的，70% 是给下一个人敢动手的。从用户角度评价结构好坏的标准不是文件数量，而是两个数——改完 src 到玩家看到变化要几步（答：1 步构建 + 1 步刷新），改坏了有多少测试会喊（答：38 个回归文件，但都是模拟 DOM，不等于真实触屏）。
四、一句话诊断
游戏把"学"设计成了收集，把"学会"外包给了节末装置和章末测验。 三层引导都在优化"怎么找到路"，没有一层在优化"我怎么知道我正在学会"。
五、系统性问题（按层）
1 目标层：没有写下来的"学会"定义
全仓唯一可执行的"学会"判据是章末测验 90%（chapter-ui.js:44）。charter / DESIGN / plan 中没有 fun hypothesis，没有 design pillar，没有"学会"的过程性定义。
直接后果：每次遇到"玩家卡住/说不清"的困惑，解法都是再加一层引导。现在三层引导并行就是这条路径的沉积物。
这不是某一次设计失误，是目标层缺位导致的结构性补丁叠加。
2 循环层：节奏倒挂——该密的地方稀，该疏的地方密
一节的实际链路：读约 10 个单元（Task 1.1 为 22）→ 收下 → 放装置 → 装置内 3–4 轮情境判断（全项目 12 个装置共 42 轮）→ 章末一次 90%。
判断全部压在节末 5–8 分钟；读的阶段 10–15 分钟零判断，只有"读懂了"的自评按钮。
修正初版诊断口径：装置内每轮提交后是有即时验证的（renderTaskWorkshop 的"这一轮已验证"modal + 原因原文）。所以问题不是"没有反馈"，是反馈密度在时间上分布倒挂——生成效应和测试效应被推到离阅读最远的位置。
量级 [假设]：以每节 10 单元、每单元阅读 40 秒计，玩家平均在"零判断"状态停留约 7 分钟，然后 5 分钟内被检验 4 次。
3 反馈层：单通道、落点错、模态打架
全 src 无 Audio / vibrate，正确与错误在听觉和触觉上完全同形。
flash 是全链路唯一动画化反馈，只用在"知识整理 +1"，且落点是 #worldFeedback（屏幕中部），不在被点的物件上——操作点与反馈点空间分离。
组装 / 配对 / workshop 的成败只写内联文本元素（#unitFeedback / #matchFeedback / #workshopFeedback），不自动清除，与 toast / modal 三套措辞并存。
首次启动时章节地图 modal 与欢迎页 modal 抢焦点（enterStudyChapter 先弹、showGameGuide(true) 后盖）。
4 引导层：三层并行、无单一真相、i18n 残缺
点击 #help 实际路径：聚光 8 步 → 说明书降为二级入口（聚光内"看完整玩法说明"）；renderGameCoach 按 carried/all/done 常驻；每章首次进还有 showStudyBrief。
8 步里 5 步是界面导航（远行册、罗盘、导入、帮助、素材箱），只有 3 步涉及学习动作，且以导航开头——顺序不是学习流程的顺序。
guide-spotlight.js 无任何测试（harness 不加载它）；kt.spotlight.v1 只写不读（死键）；state.language === 'en' 时整体绕过——英文用户看不到这层引导，而说明书有完整英文页。双语承诺在引导层是半残的。
三层的文案各说各话，没有一条共同的"现在你在学习循环的哪一格"的坐标。
5 数据层：技能覆盖在游戏里不可见
139 知识单元 / 58 技能 / 200 题的映射只活在 content/*.json|tsv 与构建脚本里，TESTING.md 用它当验收口径，玩家端从来没见过。
玩家端唯一的进度语言是"n / 总数"（数量收齐）。玩家因此被引导去优化"收齐"，而不是"掌握"。
这条与第 2 条互为因果：因为进度只数数量，所以搬运动作没有知识含量也说得过去。
六、从整体观动刀：三个同心圆
按改动半径从内到外。内环不碰契约，中环改节奏，外环改目标与契约。
内环 · 反馈归位与引导收敛（不碰契约，约 1–2 天，C 任务卡范围内）

中环 · 把判断搬回阅读旁边（改循环节奏，C 卡 + 与 B 对齐）
判断前移：每 3–4 个单元插一次 10 秒微判断，直接复用 EncounterRules / KnowledgePractice 的判定结构，不记分、不惩罚，答错即摆原文对照。
搬运压缩：读完直接 deposited，砍掉"收下 → 进背包 → 放入装置"三步；背包只保留"定位未读"的功能。
反馈升级：每次微判断正确 → 该对象本身有一次动画 + 一个 WebAudio 合成轻音效（零资源依赖）。
预期：一节的判断次数从 3–4 次变 6–8 次，"零判断"连续时长从约 7 分钟压到约 2 分钟。
代价：放弃"整理"的仪式感（这是本项目目前唯一的重节奏）；装置的地位从"唯一考点"降为"综合考场"。
外环 · 给"学会"一个可执行定义（改目标与契约，需 B + C + D）
把"学会"写成两句话并落到代码：能区分易混边界 + 能在新情境选对处理。这两件事今天的装置已经在考，只是没命名、没展示。
进度语言从"n / 总数"换成"已能判断 X / 58 技能"，章节地图卡片同改。
章末 90% 从"唯一判据"降为"抽查"，主判据改为过程记录（分散练习次数 + 错题修复历史）。
代价：碰 schemaVersion 与 A/B/C 三张任务卡的验收口径，属于契约变更，要 D 先更新接口、样例和受影响测试。

计时口径（校准第三节所有 [假设]）：每节记录四个数——阅读总时长、搬运操作次数、装置时长、微判断次数；对照假设"每节 10 单元、每单元 40 秒"。
采集方式（不需要新埋点也能开跑）：3 名新手 × 2 节（1.1 一节 + 任选非 1.1 一节），人工计时 + 结束后一对一询问"你刚才学会了什么、怎么证明"。要持续采集再给 read 数组补时间戳（属外环范围，需改契约）。
校准触发线：实测单节超过 25 分钟 → 中环必做；装置内单轮错误率超过 40% → 是内容问题不是机制问题，转 B 不改游戏。
